# Pipeline Golf

> Mock: [../pipeline-golf/index.html](../pipeline-golf/index.html)

## Elevator Pitch

**「用意された関数を並べて、INPUT を TARGET に変換する。使った関数が少ないほど強い」**

`"  Hello WORLD  "` を `"hello-world"` にする。答えは `trim ▸ lowercase ▸ replaceSpacesWithDash` の3手。

## Core Loop

```text
URLを開く（INPUT / TARGET / 使える関数 が復元される）
↓
どの関数をどの順に通せば TARGET になるか考える
↓
関数を並べる
↓
RUN（各ステップの途中結果が順に表示される）
↓
どこでズレたかを見る
↓
並べ替える / 減らす
↓
CLEAR → PAR を切りにいく
↓
SHARE URL ／ REMIX
```

## Fun Hypothesis

- **これはデバッグそのもの。** 途中結果が全部見えるので、「3手目で余計な `-` が残った」のように失敗の原因が必ず1行に特定できる。print デバッグの快感をそのままゲームにしている。
- **順序が意味を持つ。** 同じ関数の集合でも、順番を変えると結果が変わる。「関数を足す」ではなく「並べ替える」で解決する瞬間が気持ちいい。
- 関数名が `trim` / `lowercase` / `reverse` と、説明不要の語彙で構成されている。エンジニアなら初見で0秒。
- スコアが「使った関数の数」なので、Route Golf と同じく整数1個で比較できる。

## Engineer Appeal

- **関数合成 = 日常業務**。`s.trim().toLowerCase().replace(...)` を毎日書いている人には、ルール説明が要らない。
- 「この変換、もっと短く書けない？」はコードレビューで実際に起きる会話そのもの。
- 用意された関数セットが制約になっているので、**手持ちの道具で目的を達成する**という制約付きプログラミングの縮図になっている。
- 任意コードを書かせないので安全（`eval` / `Function` は不使用）。URLに載るのは関数の **ID だけ**で、コードは絶対に共有されない。

## Sharing Loop

Challenge には `{input, target, ops, par}` しか入らないので、URLは200〜260文字程度。

```text
A が「この変換、何手でできる？」と URL を投げる
↓
B が解く。RUN の途中結果で詰まった箇所が見える
↓
B が REMIX して TARGET を1文字変える → 別の問題として送り返す
```

**TARGET を1文字変えるだけで別の問題になる**ので、Remix のコストが3案で最も低い。ただし「変えた結果が解けるかどうか」は作った本人にも自明ではないため、エディタ側の解探索が必須になる。

## MVP（1日ハッカソン）

1. 安全な事前定義 Operation（10〜14個）
2. INPUT / TARGET の表示（空白が見えるように `·` などで可視化）
3. AVAILABLE OPERATIONS のクリックで PIPELINE に追加
4. PIPELINE の削除・並べ替え（↑ ↓ ✕）
5. RUN：実行中の Operation をハイライトしつつ、各ステップの途中結果を順に表示
6. TARGET との一致判定、Operations / PAR / PAR差の表示
7. URL fragment への保存・復元（version・type・壊れたら DEFAULT）
8. CREATE モード（INPUT / TARGET / 使用可能 Operation / PAR）と SHARE URL
9. REMIX
10. サンプル3問

## Cut List（上から捨てる）

1. **PIPELINE の並べ替え（↑↓）** — ✕ で消して積み直せば代用できる
2. **Operation の説明文** — 名前だけでほぼ通じる
3. **ステップごとの遅延アニメーション** — 一括表示でも成立する（ただし「デバッグ感」は落ちる）
4. **CREATE モードの解探索（AUTO PAR）** — ただし捨てると解けない Challenge が共有され得る
5. **COPY RESULT**
6. Operation の種類を10個 → 6個に減らす（実は面白さがむしろ上がる可能性がある。後述）

## Expansion（今回は実装しない）

- **引数つき Operation**：`replace(a, b)` `slice(n)` `repeat(n)`。スコアを「関数の数」から「文字数」に変えるとゴルフ性が跳ね上がる。
- **型の拡張**：文字列だけでなく配列・数値を流す（`split` → `map` → `join`）。一気に本物の関数型パズルになる。
- **複数テストケース**：1つの INPUT ではなく、3組の (input, expected) を全部通すパイプラインを作らせる。**これは「たまたま通る解」を排除できるので、優先度が高い。**
- **Daily Pipeline** / **Operation の解禁制**（レベルが上がると使える関数が増える）
- **ユーザー定義 Operation**（安全な範囲での合成関数の保存・共有）
- **手数だけでなく「実行コスト」でのスコアリング**

## Prototype Review

Mock を実際に触ったうえでの記録。企画時点の期待と、実装後に分かったことを分けて書く。

### 触ってみて良かった部分

- **Trace パネルが期待以上だった。** RUN すると
  ```
  INPUT   "··HACK·a·THON·2026·"
  ↓ lowercase
  "··hack·a·thon·2026·"
  ↓ removeDigits
  "··hack·a·thon··"
  ```
  のように1行ずつ増えていく。空白を `·` で表示したのは実装中に足した小細工だが、**これがないとゲームとして成立しなかった。** `"hack-a-thon "` と `"hack-a-thon"` の違いが見えないと、なぜ失敗したのか永遠に分からない。
- **MEDIUM の罠が3案で一番良い瞬間を作った。** `trim ▸ lowercase ▸ replaceSpacesWithDash ▸ removeDigits` と素直に組むと `"hack-a-thon-"` になる。末尾にハイフンが1個だけ残る。**惜しさの質が高く、しかも直し方は「関数を足す」ではなく「順序を変える」。** 正解は `lowercase ▸ removeDigits ▸ trim ▸ replaceSpacesWithDash`。この「並べ替えで直る」体験は、企画時に仮説として書いたとおりに機能した。
- **CREATE モードの解探索（幅優先探索）が効いた。** TARGET を打ち替えるたびに `✅ SOLVABLE 最短: 4 operations` / `🚫 UNSOLVABLE` が即座に切り替わる。Route Golf と同じく、**壊れた Challenge が共有されない**ことが構造的に保証される。
- Create が3案で最も速い。TARGET のテキストを1文字直すだけで新しい問題になる。

### 想定より弱かった部分

- **画面が動かない。** テキストが増えていくだけで、Route Golf のロボットに当たるものが何もない。企画時に「見た目が地味すぎないか」を検証項目に挙げていたが、**答えははっきり「地味」**だった。プレゼンで後ろの席から見て何が起きているかは分からない。
- **関数が多いと逆につまらない。** HARD では8個の関数を出したが、選択肢が多すぎて「考える」より「総当たりで押す」ほうが速くなった。逆に EASY の4個は、選択肢が絞られているぶん明らかに考えていた。**関数の数は5〜6個が上限**というのが触って分かったこと。企画時は「関数を増やせば深くなる」と思っていたが、逆だった。
- **たまたま通る解が作れてしまう。** INPUT が1つしかないので、その1件さえ通れば CLEAR になる。汎用的な変換を書いた感じがしない。Expansion に書いた「複数テストケース」は、余裕があれば追加ではなく**本来 MVP に入るべき要素**だと触って分かった。
- クリックで関数を積むのは楽だが、**間違えたときに ✕ を押しに行くのが地味に面倒。** キーボードで番号を打てるようにしたい。

### 操作して気持ちよかった部分 / 面倒だった部分

- 気持ちよかった：Trace の最終行が緑になる瞬間。あと `PAR -1` を並べ替えだけで達成したとき。
- 面倒だった：パイプラインの編集。↑↓✕ の3ボタンが小さく、スマホだと押しづらい。

### 「もう一回」を感じたか

**部分的に感じた。** MEDIUM の罠にハマった直後は強く感じたが、CLEAR したあとに「もっと短く」を試す動機は Route Golf ほど強くなかった。関数の数はもともと少ないので、削れる余地が体感で分かってしまう。

### Challenge を誰かに送りたいと思えるか / Remix したくなるか

- 送りたい：**エンジニア相手なら思える。** ただし「解いてみて」より「この変換どうやる？」というクイズに近い温度感。
- Remix したい：**3案で最も気軽。** TARGET を1文字変えるだけで別問題になり、SOLVABLE 判定が即座に出るので、失敗を恐れずいじれる。Remix の連鎖という意味では、実は Route Golf より回しやすいかもしれない。

### ハッカソン本番で作る価値があるか

**あるが、単独では弱い。** ロジックが軽く実装リスクも低いので確実に完成するが、**デモで見せる絵がない**のが致命的。
本番で選ぶなら、
1. 複数テストケース化（たまたま通る解を潰す）
2. 引数つき Operation とスコアの文字数化（ゴルフを本物にする）

の2つが揃って初めて、Route Golf と並ぶ企画になると思う。現状は「よくできた小道具」で止まっている。

## 実装版（GitHub Pages 公開版）で何が変わったか

| | Mock | 実装版 |
| --- | --- | --- |
| 関数 | 14種類 | **31種類**（空白/大文字小文字/抽出/切り出し/並べ替え・複製の5系統） |
| ステージ | サンプル3問 | **16ステージ**（EASY 5 / MEDIUM 6 / HARD 5） |
| TARGET | 手書き | **模範解答を INPUT に流した結果**として計算。到達不能な問題が構造的に作れない |
| PAR | 手書き | 幅優先探索の最短手数 + 1 |
| 評価 | PAR との差のみ | ★3段階（★★★＝最短） |
| 記録 | なし | localStorage にステージ別のベスト手数と★を保存 |
| CREATE | TARGET を手入力 | **RECIPE**（関数を並べると TARGET が組み上がる）を追加 |

### 実装のポイント

- 関数はすべて `id → 純粋関数` の表で持つ。URLに載るのは id だけで、
  **URLの中身を関数として解釈することはしない**（`eval` / `new Function` は不使用。テストで検査している）。
- 探索は「その Challenge で使える関数」だけに絞るので、選択肢が6〜10個でも深さ6まで現実的な時間で解ける。
  文字列が伸び続けないよう、中間結果が200文字を超えた枝は捨てている。
- ステージ定義には TARGET を書かず `solution`（模範解答）と `extras`（引っかけ）を書く。
  TARGET は起動時に計算するので、**解けない問題を出荷できない**。
